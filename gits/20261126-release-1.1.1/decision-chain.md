# 发版 1.1.1 · 决策链（decision-chain）

## D1 为什么是 1.1.1，不是 1.2.0

- 内容以**修复**为主：exe 缺图标/版本/清单、资源管理器重启后托盘消失、关托盘后应用失联、双击 exe 没反应。
- 夹带的「新增」是打包与质量设施（内嵌资源、`check-exe.ps1` 门禁），不是产品能力。
- 无破坏性变更：配置文件向后兼容、CLI 参数未变、面板与托盘行为只增不改（第二实例从"静默退出"变成"唤出面板"）。
- 因此 patch：`1.1.1`。备选 1.2.0 也说得通，但会让「只是修了个图标」听起来像加了功能。

## D2 为什么把上一条未推送的 c7a1023 一起发出去

`c7a1023`（幽灵行可发现性）当时按用户要求「不发新版」留在 `[未发布]`，至今未 push。
再压一个版本会把两条变更长期悬空，且 1.1.1 的 `[未发布]` 收口本来就包含它。
风险可控：该改动本地已实测（`--once` 6.2s、常驻 CPU 0.000s、71 项单测全绿）。

## D3 为什么拆成「代码」+「版本收口」两个提交

与 v1.1.0 的处理一致（代码 `7f63325`，版本 `ba69318`）：代码历史可单独 review，
版本收口只动版本号/CHANGELOG/README，出事时一眼能定位是哪一类改动。本次没有改写历史的需求，
`5fc69f1` 已包含全部代码与文档，release commit 保持纯粹。

## D4 为什么必须在 tag 之前提交 Cargo.lock

`release.yml` 与 `ci.yml` 都用 `--locked`。本次版本号变化必然改 lock 里的 workspace 成员版本，
本地已用 `cargo build --locked --release` 复跑通过；若漏提交，tag 上的 CI 会直接失败，
而 tag 已推到远端，修起来要删 tag 重打。

## 风险与回滚

- 风险 1：CI 在 tag 上失败（lock/版本/资源门禁/self-test）。缓解：本地已按 CI 同口径全跑。
- 风险 2：`release.yml` 的 `contents: write` 权限被仓库策略收紧 → Release 发不出去。缓解：`gh run view` 看日志定位。
- 回滚：`gh release delete v1.1.1 --yes` + `git push --delete origin v1.1.1`；代码本身不受影响。

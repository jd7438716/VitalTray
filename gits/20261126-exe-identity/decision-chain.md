# exe 身份补齐 · 决策链（decision-chain）

## D1 为什么自己写 build.rs 调 rc.exe，而不是用 embed-resource / winresource

- 那两者本质也是「找 rc.exe → 编 .res → 交给链接器」，只省掉 ~60 行代码，却多一个会拖慢并可能
  因网络失败而中断的构建依赖。
- 本项目「零第三方运行时」的纪律延伸到构建期更一致：依赖只有 `windows-sys`，构建依赖 0。
- 代价：得自己找 rc.exe。做法是按 `%ProgramFiles(x86)%\Windows Kits\10\bin\<ver>\<arch>\rc.exe`
  取版本号最高的一档，`RC` 环境变量优先；**找不到只 `cargo:warning` 不失败**，保证没装 SDK 也能 build，
  缺陷交给 `check-exe.ps1` 在发布前拦。

## D2 为什么清单里带 comctl32 v6

没有清单的 Win32 程序拿不到视觉样式：`TrackPopupMenuEx` 画出来是 Win2000 那种方角灰菜单，
和自绘面板的观感打架。清单同时补齐 DPI（PerMonitorV2，运行时那句 `SetProcessDpiAwarenessContext`
现在会被系统忽略，代码里已有的兜底逻辑不受影响）和 Win10/11 `supportedOS`。

## D3 为什么版本号从 CARGO_PKG_VERSION 现生成

v1.0.0 → v1.1.0 时 README 的「当前版本」忘记跟着改（这次一并修正）。手写 .rc 里的版本号
必然再漂一次，所以 build.rs 直接读 `CARGO_PKG_VERSION`，`Cargo.toml` 是唯一事实源。

## D4 为什么托盘兜底改成「第二个实例唤出面板」，而不是加全局热键

「菜单里关掉托盘图标 → 应用失联」是自锁死循环。两条出路：

- 注册全局热键（如 Ctrl+Alt+B）：会引入热键冲突面，且用户不知道有这个键。
- **第二次运行 exe 唤出面板**：用的是用户唯一会做的动作（再双击一次），零新 UI、零热键占用；
  顺带修掉「双击 exe 毫无反应、以为程序坏了」的老毛病。

选后者。同时关托盘那一刻弹一句说明，把恢复路径写在用户眼前。

## D5 为什么图标竖向且「肥」

- 竖向：托盘 16px 槽位是接近正方形的，横向电池（旧字形）只能占中间一条，上下空；竖向能把槽位用满。
- 壳宽 46%：第一版 35% 在 16px 下像根细管子，用户反馈「做肥一点」；46% + 壳厚 5.5% 在 16/32/48 都结实。
- 绿色 `#6CCB5F`：直接取状态色板里 Good 的深色值，品牌色和状态色同源，不多造一个绿。
  **托盘图标仍按状态上色**（低电红壳 / 充电蓝 / 无数据斜线），品牌绿只出现在静态的 exe 图标上。

## 风险与回滚

- 风险 1：rc.exe 在 CI 找不到 → 构建成功但 exe 无资源。缓解：`check-exe.ps1` 紧跟在构建步骤后，失败即中断发布。
- 风险 2：清单 XML 写错会让进程起不来（SxS 错误）。缓解：`mt.exe -inputresource` 读回校验 + 本地实跑
  `--version` / `--self-test` / 面板。
- 风险 3：`TaskbarCreated` 处理里 `readd()` 失败会静默丢图标。当前只记日志；极端情况下用户重启应用即可恢复。
- 回滚：图标/清单都是构建期注入，撤掉 `build.rs` 与 `assets/` 即回到无资源状态；运行时改动均可单独 revert。
